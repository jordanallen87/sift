# ADR 0003: Vehicle Catalog and Normal Case Creation

Status: accepted
Date: 2026-08-29

## Context

The car-purchase hero previously had exactly one entry point: `startDemo({ demoId: 'car-purchase' })`, which resets to the checked-in four-candidate fixture (RAV4/CR-V/CX-5/Outback). The project owner supplied an extended product brief (relayed from ChatGPT, pasted verbatim into this task's own context) whose core ask is: "Sift should be useful as a normal vehicle-comparison website before ChatGPT/WebMCP is involved" — a user should be able to browse a real vehicle catalog, build a 2-5 candidate shortlist, and create a real, persisted `car-purchase` case from it, with the deterministic four-car scenario preserved unchanged as the reliable demo path.

Two architectural facts, confirmed by reading the current implementation (not assumed from the brief), bound what is honestly achievable this task:

1. **`upsertOption` already supports partial, catalog-sourced entities.** `CommandService.upsertOption` (`apps/agent/src/services/command-service.ts`) writes an `AttributeRecord` only for attributes explicitly supplied in the call, always `status: 'asserted'`; it never fabricates a value for an omitted `AttributeDefinition`, matching the manual `OptionEditor` flow that already exists. This means a catalog-created candidate can supply known facts (make/model/year/trim/body style/drivetrain/powertrain/combined MPG) and simply omit facts the catalog cannot know (price, mileage, dealer terms, safety ratings, ownership cost) — no contract or reducer change needed to represent "explicit unknown" for those.
2. **The live `car-purchase` investigation engine is not generic.** `apps/agent/src/runtime/car-purchase-engine.ts` and `runtime/scripted-beats/car-purchase.ts` implement a two-round, fully scripted Strands Graph run written specifically around the four named fixture candidates: hardcoded candidate ids (`candidate-rav4`, `candidate-crv`, `candidate-cx5`, `candidate-outback`), a hardcoded hard-constraints summary sentence naming them, and a hardcoded teaser-price source id. `packages/core` has no candidate-scoring/ranking function of its own — recommendation synthesis exists only inside this scripted engine. There is no reasonable way to make `requestInvestigation` produce a truthful, evidence-gated recommendation for an arbitrary catalog-built shortlist without building a genuinely new, generic investigation engine — a materially larger undertaking than this task, and one the source brief itself did not scope with the detail (real safety/reliability data source, real deal-normalization logic for arbitrary listings) that would be required to do honestly.

## Decision

1. **Vehicle catalog data source: EPA fueleconomy.gov bulk CSV**, a US-government work in the public domain (17 U.S.C. § 105) — verified live during this task (`https://www.fueleconomy.gov/feg/epadata/vehicles.csv`, `HTTP 200`, `content-type: application/octet-stream`). No license or attribution obligation applies to reuse or redistribution, but Sift attributes it anyway as accurate sourcing practice (`docs/reuse-attribution.md`). A bounded, curated transform (`scripts/`-adjacent, not checked in as a build step; the output is checked in directly) selects 44 popular make/model families across the two most recent model years present in the source (2025/2026 relative to this task's environment clock) and at most 2 distinct drivetrain/powertrain variants per model-year, producing 151 records / ~60KB — real government-published data, not fabricated, and small enough to ship as a static JSON asset with no runtime network dependency (docs/engineering-principles.md "Fixture mode must execute the complete product without network access after installation").
2. **New package `@sift/catalog`** owns the static dataset, a Zod `VehicleCatalogRecordSchema`, bounded/deterministic query functions (`listYears`, `listMakes`, `listModels`, `searchVehicles`), and the one adaptation boundary from a catalog record to a `car-purchase` pack option's attributes (`mapCatalogRecordToOptionAttributes`). This package is a shared dependency of `apps/agent` (server-side catalog routes) and `apps/web` (so the mapping logic used to build a real `upsertOption` call is identical wherever it runs, matching docs/engineering-principles.md's "same command implementation" principle by construction — there is exactly one mapping function, not a client copy and a server copy).
3. **New generic case-creation command, `startCase({ packId })`**, sibling to `startDemo` rather than an overload of it. It creates an empty case pinned to the given pack (the same `instantiateCase` core function `startDemo` already uses, with zero seed entities) with no dependency on the closed `DemoId` enum. The web app then calls the existing, unmodified `upsertOption` once per shortlisted vehicle. No changes to `upsertOption`, the reducer, or any evidence/readiness logic were needed for this — confirming point 1 in Context.
4. **`requestInvestigation` on a catalog-built (non-demo) `car-purchase` case returns an honest failure, not a crash or a fabricated result.** `car-purchase-engine.ts` gains a narrow, exact guard (`isDeterministicCarPurchaseDemoCase`: the case's entity id set equals exactly `{candidate-rav4, candidate-crv, candidate-cx5, candidate-outback}`) checked before the scripted graph runs. A catalog-built case fails the run immediately with a clear `run.failed` activity event explaining that guided AI investigation currently runs only against the deterministic demo case, while every other capability — browsing, shortlisting, comparison, listing-detail entry via the existing `OptionEditor`, criteria changes, custom concerns, evidence you submit yourself via `sift_submit_source`/`sift_set_evidence_disposition`, and full WebMCP context — remains completely real and functional against the catalog-built case. This is a deliberate, disclosed scope boundary (docs/engineering-principles.md "state honestly ... not a reason to fake or block the rest of the build"), not a silent gap. Building a genuinely generic investigation engine (real safety/reliability/deal data for arbitrary vehicles) is out of this task's scope and is recorded as a known limitation, not attempted partially.
5. **Landing IA**: the launcher gains one primary action, "Compare vehicles" (opens the new catalog browser/shortlist flow), placed above the two existing demo cards, which move under a visually secondary "Or try a finished example" group heading. `DemoLauncher` keeps both existing `startDemo` cards, their exact copy ("Choose our next car" / "Investigate my energy bill"), and their exact `data-testid`s/behavior completely unchanged — only their visual grouping/hierarchy changes, avoiding an unnecessary, wide-blast-radius rename across the Playwright journeys and submission demo scripts that already quote this exact copy verbatim. The new primary action is purely additive.
6. **`OptionEditor` is reused unmodified** for listing-detail enrichment (price, mileage, dealer label, listing URL) on a catalog-created candidate — it already supports editing any subset of a pack's declared attributes on an existing entity, satisfying spec brief §10/§11 with zero new code.

## Consequences

- No changes to `packages/contracts`' `CaseState`, `EntityRecord`, `AttributeValue`, or any evidence/readiness/reducer logic. The only contract addition is `StartCaseInputSchema`/`StartCaseInput`, structurally trivial (`{ packId }`).
- No changes to the `car-purchase` pack manifest (`packages/packs/src/car-purchase.ts`). Every catalog field the EPA source can supply already has a matching pack attribute; no new attributes were needed, honoring the brief's own "do not casually expand the pack" instruction (§8).
- `sift_get_case_context` and every other WebMCP tool needed no code changes to work against a catalog-built case — confirmed by reading `apps/web/src/model-context/*.ts`, which projects `CaseState` generically with no demo-specific branching. This task adds *tests* proving that (a real gap in coverage, not in implementation), not new production code.
- The demo-guard in `car-purchase-engine.ts` is the one behavior change to existing, already-shipped code in this task; it is purely additive (an early-return before the scripted graph runs) and does not alter round-1/round-2 behavior for the real deterministic demo case, which still matches its own exact candidate-id set.
- A future task could replace the demo-guard's honest failure with a real generic investigation engine (e.g., a deterministic core-level scoring function against known attributes and user-supplied evidence, decoupled from the scripted Strands narrative). That is explicitly out of scope here and is recorded in the completion report's known limitations, not silently implied as "already working."
- `docs/reuse-attribution.md` gains a new dataset-attribution entry for the EPA source, per docs/engineering-principles.md's "Dataset licensing/attribution is complete and truthful" requirement.
